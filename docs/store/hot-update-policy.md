# 前端热更新 · 商店合规纪律

> 适用范围：所有应用商店渠道（Mac App Store / Microsoft Store / Flathub）。
> 结论：前端热更新（FrontendBundleManager，签名 zip 替换 WebView 前端）**可以保留**，
> 但必须遵守本文边界。依据条款均为 2026-09 核实版本。

## 政策依据

- **Apple**：审核指南 2.5.2 禁止"下载改变功能的代码"，但开发者协议 §3.3.1(B)
  豁免**系统 WebKit/JavaScriptCore 执行的解释型代码**，前提：
  ① 不改变 app 主要用途；② 不形成应用内商店；③ 不绕过签名/沙盒等安全机制。
  我们的热更新跑在同一沙盒 WebView 内、只加载自己签名的官方包（ed25519 验签 +
  min_shell_version 版本下限 + 失败回退壳内置资源），属于合规范式
  （与 Capacitor Appflow / EAS Update 同一路径）。
- **Microsoft**：政策 10.2.2 禁止"通过动态代码根本改变或扩展已描述的功能"。
  因此仅把与已描述功能一致的修复和改进纳入热更新；是否接受该具体实现，仍以商店审核结果为准。
- **Flathub/Snap**：无限制，只要不替换商店托管的二进制本体。

## 发布边界（每次热更新发布前自查）

| ✅ 可以走热更新 | ❌ 必须走商店发版 |
|---|---|
| bug 修复、性能优化 | 全新功能模块（如新增"白板""日历"级功能） |
| UI 调整、文案、交互优化 | 新原生能力：新 Tauri 插件、新权限、新 entitlement |
| 已有功能的改进 | 改变数据收集实践（会使商店隐私标签失真） |
| 内容与配置变更 | 使商店描述/截图不再准确的变更 |

## 硬性红线（三家通用）

1. 热更新包**只能是自有签名发布**，绝不执行用户输入或第三方提供的代码
   （2026-03 苹果 2.5.2 严打针对的正是"执行任意生成代码"的应用）。
2. 不得通过热更新解锁付费功能或绕过 IAP 规则。
3. 隐私实践变化（新收集字段、新第三方 SDK）必须随商店版本更新隐私标签。
4. 每次热更新在发布记录中注明"本次更新对应的已审核功能范围"，留存备查。

## 应急开关

任一商店审核提出异议时，用保守构建重新提交该渠道（其他渠道不受影响）：

```
npm run build:msstore:no-hotupdate   # Microsoft Store 示例
```

保守构建编译时关闭 `frontend-hot-update` 特性，app 始终使用壳内置前端资源，
行为与"无热更新"完全等价。
