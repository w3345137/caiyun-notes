# 商店渠道与前端更新边界

> 目标：成熟渠道尽可能仅保留官方商店安装包；原生壳由商店分发更新，前端仍争取保持快速发布能力。此目标不等于三个商店都允许同一种可执行前端包热更新。

## 渠道决定

| 渠道 | 原生壳 | 前端资源 | 当前发布规则 |
|---|---|---|---|
| Microsoft Store | 只由 Store 更新 MSIX | 用户要求候选版保留签名前端 ZIP 更新，失败回退包内资源 | 原生整包自更新和其他平台安装包下载入口关闭；代码热更新仍有 10.2.2 审核风险 |
| Mac App Store | 只由 Store 更新原生壳 | 用户指定候选版保留签名前端 ZIP 更新 | 此为待 Apple 实际审核的高风险方案，不能把构建通过等同政策认可；保留无热更新回退构建 |
| Flathub | 由 Flathub 更新 Flatpak | 待真包及审核验证 | 不预设“无限制”；确认沙盒、网络访问、离线启动和软件源规则后再定 |

现有官网直装渠道仅用于商店尚未覆盖的平台、迁移中的老用户和必要的故障回退。不能在商店页面公开、老用户迁移与本地数据保全验证之前删除下载入口或提高统一壳门槛。

## 为什么不能三家一刀切

- Microsoft Store 2026-09-22 审核曾指向应用内“下载 App”弹窗；跨平台安装包入口必须继续在商店版隐藏。用户后来明确要求微软商店版也保留签名前端 ZIP 热更新。微软政策 10.2.2 对通过动态代码根本改变或扩展已描述功能设限；签名与同源只降低供应链风险，不证明商店已经认可这种更新方式。上线前须如实核对功能描述与实际更新范围。
- [Apple App Review Guidelines 2.4.5(vii) 与 2.5.2](https://developer.apple.com/app-store/review/guidelines/) 要求 Mac App Store 应用通过商店分发更新，并限制下载、安装或执行会引入或改变功能的代码。当前 `FrontendBundleManager` 将完整 JS 前端 ZIP 下载到本地并替换运行资源；不能仅凭 WebKit 执行或签名就宣称符合规则。用户选择先以保留机制的候选版接受实际审核；提交说明必须如实披露，不能用审核未发现代替长期合规判断。
- Flathub 的打包和沙盒约束与前两者不同，也不能把“无原生二进制变化”视为唯一合规条件。

## 每次发布的工程门槛

1. **原生能力变更**（Tauri 插件、权限、entitlement、系统集成、WebView 约束）走相应商店发版，不通过前端包绕过审核。
2. **前端签名包**只由官方发布、验签后安装，固定回退到壳内资源；不得下载执行用户或第三方提供的任意代码。
3. **功能、隐私或收费模型变化**若使商店描述、截图、隐私披露或审核范围失真，先更新商店材料/版本，再扩大热更覆盖。
4. **按渠道裁决版本门槛**：官网壳的最低版本不能自动锁住商店壳；商店渠道不得提示下载官网安装包来完成原生更新。
5. **迁移验收**要覆盖旧官网版到商店版的账号、IndexedDB、离线未同步日志和本地附件；不能以“重新安装能登录”代替数据无损验证。
6. **先实测再收口**：真实商店包安装、升级、断网启动、签名前端更新、失败回退和审核通过后，才逐步移除对应平台的官网直装入口。

## 应急开关

Microsoft Store 的默认构建启用签名前端热更新；需要回退为只用包内前端时执行：

```text
npm run build:msstore:no-hotupdate
```

禁用后该商店包使用内置前端。两种构建都不包含原生整包更新器；切换构建方式须发布新的 MSIX，不能通过服务器配置为旧包添加或移除这项能力。

Mac App Store 的保守回退构建命令为 `npm run build:appstore:no-hotupdate`。无论是否启用签名前端更新，原生整包自更新都必须关闭，跨平台安装包下载入口不得出现在商店界面。
